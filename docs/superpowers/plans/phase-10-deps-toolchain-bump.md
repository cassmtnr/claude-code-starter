# Phase 10: Dependency & Toolchain Bump

> Numbering note: Phases 1–9 in `ROADMAP.md` track in-feature work. Phases 10+ track codebase overhaul. Future overhaul phases follow this numbering.

## Goal

Bring all dependencies and the runtime/toolchain floor current after ~2 months of drift. Single bundled bump, fix breaks inline, verify CI green via a `develop → main` PR, ship as one release through the existing semantic-release pipeline.

## Scope

`package.json` deps, `engines.node`, `tsup` build target, Biome schema reference, CI workflow Node version. Out of scope: code refactoring or behavior changes beyond what the bumped toolchain forces.

## Rationale

**Node 22.14+ floor (verified against npm registry):**
- `@commitlint/cli@21` requires `node >=22.12.0`
- `semantic-release@25` requires `node ^22.14.0 || >=24.10.0`
- `semantic-release@25` transitively requires `@semantic-release/npm@13` and `@semantic-release/github@12`, both of which independently require `node ^22.14.0 || >=24.10.0`. This means the 22.14 floor holds even if someone tries to bump only the `semantic-release` top-level package — the transitive plugins enforce the same requirement.

The intersection is `>=22.14.0`. Taking the CI-tooling majors forces this floor; there is no path that takes them while keeping Node 20. Trade-off accepted: published package now requires Node 22.14+, narrower user base than Node 20. Reasonable assumption — users running a Claude Code helper run current Node.

**Why take the CI-tool majors at all:** They affect the release pipeline, not the published artifact's runtime behavior. The risk surface is "CI breaks until config is adjusted" — bounded, fixable, not user-facing.

**TypeScript 6.0:** Real risk. Strict project, ~8.2k LOC. Actual breaking changes are unverified until we run `tsc`; intentionally not speculating. Strategy below.

**Biome 2.4:** Minor. New rules may flag existing code. Strategy below.

## Test plan

Run in order. Stop on first failure, fix, continue.

1. `bun install` — lockfile refresh, no install errors
2. `bun run typecheck` — TS 6.0 sanity
3. `bun run check` — Biome 2.4 sanity
4. `bun test src/cli.test.ts` — 269 unit tests pass (covers source logic)
5. `bun run test:e2e` — built artifact `--version`/`--help` invocations work (covers symlink path / startup, not pipeline behavior)
6. **Prerequisite for the next two steps:** verify `node --version` is ≥22.14 locally. `npx` uses system Node, not Bun's runtime; commitlint@21 and semantic-release@25 will refuse to start on lower versions, and the failure message will look like a config error.
7. `npx commitlint --from HEAD~5 --to HEAD` — config still parses under v21
8. `npx semantic-release --dry-run --no-ci` — pipeline still validates against v25
9. Open a PR from `develop` to `main`, observe the PR Check workflow green (the workflow is triggered on `pull_request` to `main`, not on push to `develop`)

Steps 7–8 are CI-config sanity. Step 9 is the actual gate — local Node may differ from CI Node and the bump must work on the CI runner specifically.

## Strategy for in-flight breaks

**TS 6.0 breaks at step 2:** Fix in place if the fix is mechanical (added type assertion, narrowed call site, swapped removed flag, updated a `tsconfig.json` compiler option that was renamed or removed). Stop and surface if the fix would require changing an exported API, removing functionality, or rewriting a module's interface. Judgment: would a reviewer call this "deps bump fallout" or "redesign"? The former, do it. The latter, surface. `tsconfig.json` is in scope for surgical fixes.

**Biome 2.4 new rules at step 3:** Auto-apply Biome's `--write` for safe fixes. For new rule violations that aren't auto-fixed: either fix the code or add `biome-ignore` with a one-line `why` comment. Do not disable a rule project-wide as a workaround.

**Commitlint/semantic-release config breaks at steps 7–8:** Update `.commitlintrc.json` / `.releaserc.json` as required. Compatibility of the current configs against v21/v25 is not pre-verified — the dry-run is the verification. If config changes are needed, apply them, then re-run.

**CI breaks at step 9:** Already in scope (CI Node version pin is part of this phase).

## Rollback

**Before pushing to `main`:** The work lives on `develop` until step 9 is green. A `git reset --hard` on the local branch wipes everything if needed. Cheap.

**After pushing to `develop`, before `main` merge:** `git revert <sha>` on the develop branch restores prior state. CI re-runs against reverted code.

**After `main` merge but before semantic-release publishes:** Revert PR to `main`, semantic-release picks up the revert as the next release.

**After semantic-release publishes to npm:** Harder. `git revert` doesn't unpublish. Recovery path: `npm deprecate claude-code-starter@<bad-version> "..."`, then ship a fix-forward patch release. Step 9 of the test plan is specifically the gate that should prevent reaching this case.

## Constraints

- Bun-managed lockfile only. Do not run `npm install` or `yarn install` at any point — would create a competing lockfile.
- Do not bump beyond latest stable published version. No pre-releases, no betas.
- All git operations performed by the user, not by the implementing agent (per project conventions).

## Non-goals

- Replacing `prompts` with `@clack/prompts` (redesign, not a bump — defer)
- Source-level refactoring beyond what TS 6.0 forces
- Migrating CI from Bun to npm/pnpm
- Changing the `semantic-release` branch strategy (currently `main` only)
- Updating the embedded analysis prompts in `src/prompt.ts` (covered by Phase 12 re-baseline)

# Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Execute the bumps and toolchain alignment defined in the spec above as a single bundled change, verified gate-by-gate, ready for the user to commit and PR `develop → main`.

**Architecture:** Sequential bumps ordered low-risk → high-risk. Each task isolates one bump (or one tightly-coupled group) so the failure attribution is unambiguous if a gate fails. No intermediate commits — the implementing agent stages changes, the user commits at the end as one logical unit per the spec's "single bundled bump" constraint.

**Tech Stack:** Bun (lockfile + test runner), TypeScript 6, Biome 2.4, tsup, semantic-release 25, commitlint 21.

**Execution invariants** (apply to every task):
- All `git` operations are performed by the **user**, never by the implementing agent. Tasks may stage with `git add` only if explicitly noted; they never commit, push, branch, or merge.
- No `npm install` / `yarn install` — Bun-managed lockfile only.
- If a gate fails for a non-mechanical reason (per the spec's "Strategy for in-flight breaks"), **stop the plan and surface to the user**. Do not "press on."
- On stop-and-surface: leave the working tree as-is so the user can inspect the partial state. Do NOT `git reset` or `git stash`. The user decides whether to roll back (`git reset --hard origin/develop` after committing nothing) or to continue manually.
- Working directory stays on the existing branch (`develop`); no branch creation needed.
